01 · Gốc rễ vấn đề

Vì sao phải "dạy việc" cho AI?

Chưa xong — quăng nguyên đầu việc cho AI chưa đủ, vì ba giới hạn bẩm sinh của model:

① Kiến thức chung chung
Model biết Magento là gì…

…nhưng không biết format audit của BSS, convention code của team, quy trình ET của công ty.

② Không có trí nhớ
Mỗi session bắt đầu từ số 0

Hôm qua bạn giải thích kỹ đến đâu — session mới quên sạch. Model là stateless.

③ Context = bộ nhớ duy nhất
Muốn AI biết → phải nạp vào context

Nhưng context có hạn — không thể nhét tất cả kiến thức vào mọi lúc.

⊕ Bài toán thật sự

Đưa đúng kiến thức vào context, đúng lúc cần — mà không làm context phình. Mọi kỹ thuật "dạy AI" đều xoay quanh bài toán này, và Skill là lời giải có tổ chức nhất cho kiến thức dạng quy trình.

02 · Sự khác biệt

Prompt liên tục vs có Skill

✕ Chỉ prompt
  • Mô tả lại quy trình mỗi lần — dài, sót bước
  • Kết quả mỗi lần một kiểu, format trôi dạt
  • Chất lượng phụ thuộc người gõ hôm đó
  • Kinh nghiệm hôm nay, mai gõ lại từ đầu
    • ✓ Có skill
  • Một lệnh / — quy trình khóa trong file
  • Ai chạy cũng ra một chuẩn
  • Junior chạy được quy trình của senior
  • Sửa file một lần, mọi lần sau hưởng
    • ⊕ Bản chất

    Prompt là nói miệng — skill là quy trình được văn bản hóa. Khác nhau như công ty có SOP và không có SOP.

    05 · Build cho đúng — tiêu chí sàng lọc

    Việc này có đáng làm skill?

    ✓ Build khi…
  • Đã làm 2–3 lần rồi — và chắc chắn còn lặp lại
  • Các bước viết ra được, giao junior làm được
  • Có format đầu ra chuẩn để khóa lại (có sẵn "đáp án")
  • Kết quả sai dễ phát hiện — đầu ra kiểm chứng được
    • ✕ Đừng build vội khi…
  • Việc one-off, đang dò đường
  • Bản thân quy trình còn thay đổi hàng tuần
  • Thiên về judgment, ít bước cố định ("review design này")
  • Không mô tả nổi thế nào là "xong"
    • ⊕ Rule of thumb

    Không viết nổi checklist cho con người thì cũng không viết nổi cho Claude. Skill chỉ là checklist của bạn, được làm cho chạy được.

    05 · Build cho đúng — quy trình

    Build kiểu TDD — "test" trước, SOP sau(TDD — Test-Driven Development: viết test trước, viết code sau)

    STAGE 1 · CONTRACT
    Chốt expected output
    Viết đầu ra mẫu (cột CSV, section) trước khi viết hướng dẫn — như viết test trước khi code.
    STAGE 2 · SOP
    Viết như docs onboarding
    Lệnh cụ thể, expected result từng bước, đánh dấu chỗ BLOCKING cần hỏi người.
    STAGE 3 · IDENTITY
    Naming & trigger
    Folder = name: trong frontmatter. Description = điều kiện trigger, viết dạng "dùng khi…".
    STAGE 4 · PERMISSIONS
    Least privilege
    Read-only thì không cấp Write. File nhạy cảm (env.php) → human chạy lệnh.
    STAGE 5 · SHIP & RUN
    MVP ~20 dòng
    Chạy thật ngay, fix như fix bug — cầu toàn từ ngày đầu là cái bẫy.
    ⊕ Vì sao "test trước"?

    Đầu ra mẫu chính là unit test của skill: chạy xong, diff kết quả với "đáp án" là biết pass/fail. Không có contract = không có cách nghiệm thu.

    07 · Bug log — của chính bộ skill, không phải site khách

    Bug của bộ skill → patch thành rule (1/2)

    BUG #1 · FORMAT DRIFT — output trôi format

    Để Claude tự gõ CSV như gõ văn bản → mỗi lần chạy ra một kiểu: lệch cột, mất dòng section. Import vào Excel chuẩn công ty là gãy.

    →
    PATCH → RULE

    Format phải do code quyết, không do model: sinh CSV bằng python csv + UTF-8 BOM, dòng section gắn marker # do not remove.

    BUG #2 · CREDENTIALS EXPOSURE — lộ thông tin nhạy cảm

    Một checkpoint cần số liệu DB — mà credentials nằm trong env.php. Cho automation đọc file đó = giao user/pass DB cho model.

    →
    PATCH → RULE

    Skill cấm đụng env.php — chỉ in sẵn 4 lệnh PHP an toàn, người chạy tay rồi paste kết quả lại. Số liệu vào, credentials không ra.

    BUG #3 · FALSE POSITIVE — kết luận sai

    Grep config thấy gzip ON → skill báo "đã bật nén". Nhưng response thật không có header content-encoding — server thực tế không nén.

    →
    PATCH → RULE

    Kết luận phải đo từ hành vi thật: bắt network request (Chrome DevTools), fallback curl -I. Config là lời hứa — response mới là sự thật.

    ⊕ Điểm chung

    Không rule nào sinh ra từ bàn thiết kế — tất cả đều là patch sau một lần chạy thật bị gãy. Skill cũng có vòng đời như code: ship → bug → fix → bền dần.

    07 · Bug log — của chính bộ skill, không phải site khách

    Bug của bộ skill → patch thành rule (2/2)

    BUG #4 · CONTEXT OVERFLOW — tràn bộ nhớ phiên

    Chạy 2 skill liền trong 1 session → context gần đầy, Claude âm thầm bỏ checkpoint cuối. Không error, không warning — chỉ thiếu kết quả.

    →
    PATCH → RULE

    1 skill = 1 session mới — ghi vào README như quy định vận hành. Context như RAM: đừng chạy sát trần.

    BUG #5 · OVER-PERMISSION — cấp thừa quyền

    Skill chỉ cần đọc nhưng cấp luôn quyền Write "cho tiện". Một lần model đi lạc hướng — ghi nhầm vào file thật của dự án.

    →
    PATCH → RULE

    allowed-tools = whitelist đích danh: cần tool nào khai đúng tool đó. Least privilege — như phân quyền DB user, không GRANT ALL.

    ✓ Definition of Done — trước khi commit một skill
  • Junior đọc SKILL.md tự chạy được — zero câu hỏi?
  • Expected output (cột, section, ví dụ) nằm ngay trong skill?
  • Các điểm BLOCKING cần hỏi người — đã đánh dấu?
  • allowed-tools đã least-privilege?
  • Đã chạy thật ≥ 1 lần và diff kết quả với "đáp án"?
